## 一、为什么单独立项

PLAN2 里有两项验收**没达标**，而且根因是同一个：

| 任务 | 目标 | 实测 | 差距 |
|---|---|---|---|
| T1 属性跨镜一致率 | > 60% | 28.4%（车型）/ 37.2%（颜色） | 未达，但已是基线的 3.4~4.5 倍 |
| T7 跨镜观测链 IDF1 | 「拼对」 | 0.4955（IDP 0.6481 / IDR 0.4011） | 39.5% 的车**完全不扩展** |

两者的共同根因（PLAN2 已记录）：**用错域的预训练权重 + 裁剪图分辨率过低**。
这不是 bug，是**已知局限**。要真正达标只有两条路：换训练域更近的权重，或**域内微调**。
本文评估后者的成本，避免把它和本轮修复混算。

## 二、域差异到底有多大（实测取证）

### 2.1 分辨率：**不可通过重裁提升**（这条便宜路已排除）

| 项 | 实测值 |
|---|---|
| 源视频分辨率 | 1920×1080（`train/S01/c001/vdo.avi`） |
| 裁剪图中位尺寸 | **116×94 px**，中位面积 **10,716 px** |
| 面积 < VeRi 训练分辨率 256×256（65,536 px） | **88.5%** |
| 面积 < 64×64（4,096 px） | **24.0%** |

**取证过程（排除「裁剪时被降采样」这一假设）**：
随机抽 300 条检测，比较 `crop_path` 实际尺寸与检测 bbox 尺寸，比值
**W_crop/W_bbox 中位 = 1.000**（min 1.000 / max 1.000）；
再把 `dets[0]` 按其 bbox 从**源视频**逐帧定位重裁一次 —— 得到 **339×158**，
与已保存裁剪图 **339×158 逐像素同尺寸**（面积均 53,562 px）。

→ **结论：裁剪图就是原生分辨率，目标在画面里本来就这么小。**
重裁、换更高质量的解码都不会增加任何信息量。**这条最便宜的优化路径被证伪。**
（注：JSON 里的 `bbox_size` 字段是 `'large'` 这类**分类字符串**，不是尺寸，勿误用。）

### 2.2 视角域

| 数据集 | 视角 |
|---|---|
| VeRi（ReID 权重训练域） | 收费站**正视**，目标占画面比例大 |
| AICity22（本数据集） | 高处路口**侧俯视**，目标小且形变/遮挡严重 |

### 2.3 可分性实测（T7 已记录）

同车跨镜余弦 0.326 vs 异车跨镜 0.204，**d-prime 仅 0.78**（分布高度重叠）。
作为对比，VeRi 官方对该权重报告 R@1 = 97.0%。差距不是实现问题。

## 三、决定性差异：**两个模型的标签可用性完全不同**

这是本文最重要的一条，直接决定成本量级。

| 模型 | 域内标签是否存在 | 微调可行性 |
|---|---|---|
| **ReID**（fast-reid `veri_sbs_R50-ibn`） | ✅ **天然存在**：`vehicle_id` 就是 GT 全局身份（与 GT track_id 同源，230 个 ID 已核实 100% 命中 GT） | **可行**，无需人工标注 |
| **属性**（PULC `vehicle_attribute`） | ❌ **完全不存在**：AICity22 GT 只有 bbox + ID，**没有颜色/车型真值**。T1 是**零样本**跑出来的 | **被阻塞**，必须先人工标注 |

→ 因此「微调」不是一件事，是**两件成本差一个数量级的事**：ReID 可直接开工，
属性微调的前置成本是**人工标注**。

## 四、成本估算

### 4.1 ReID 微调（可行，成本可控）

**可用训练数据**（实测）：

| 项 | 值 |
|---|---|
| 多摄像头身份（可做跨镜训练） | **218** |
| 这些身份的裁剪图合计 | **68,334**（中位 211.5 张/身份，最少 5 张） |
| 单摄轨迹数 | 926 |

**算力估算（有推导，非拍脑袋）**：
T2 实测 ReID 推理 **121 img/s**，全量 68,334 张耗时 565 s。
训练一步约等于 3× 推理开销（前向+反向+优化器）⇒
单 epoch ≈ 565 × 3 ≈ **28 min** ⇒ **20 epochs ≈ 9.4 小时 GPU**。
（AICity22 数据非商用，此项只能在学术/研究口径下做，见 T11 许可说明。）

**风险（如实标注）**：218 个身份对度量学习来说**偏少**（VeRi 是 575 ID / 37,878 图）。
低分辨率 + 小样本，微调**可能过拟合**。故下面给了最小验证实验来先证伪。

### 4.2 属性微调（被人工标注阻塞）

AICity22 无属性真值。要微调就得先标注。低成本方案是**标注到「轨迹级」而非「检测级」**：

- 926 条单摄轨迹 × 每轨迹主导颜色/车型 ⇒ 约 **1,300 个决策**（颜色+车型各一次）
- 按 ~5 s/决策估算 ⇒ **约 1.8 小时**人工（不含质检）
- 但轨迹级标签比检测级弱（T1 已实测**轨迹多数投票无效**：车型 +1.4% / 颜色 −2.3%），
  故这条路的收益需要打折看待。

**推断**：即便标注完成，属性模型的上限仍受 116×94 px 的输入分辨率压制。

## 五、预期收益（**推断，非实测**）

本文**不承诺任何具体数字**。可以说的只有方向：

1. 域内微调**大概率能改善** d-prime 与 IDF1 —— 因为当前是"用错域的权重"的典型后果。
2. 但**不太可能**把 IDF1 从 0.4955 推到"拼对"的水平：24% 的裁剪图小于 64×64，
   这部分样本的信息量已经损失在成像阶段，任何模型都救不回来。
3. 属性侧即便微调，也要先解决标注问题；而 T1 的残余误差已经直接造成
   **7/218 的检索查询被属性粗筛把目标滤掉**（见 PLAN2 T7-a）。

## 六、建议：先做一个可证伪的最小实验（成本最低）

不要直接上 9.4 小时的微调。先做这个：

1. **按身份切分**：218 个身份里取 80% 训练 / 20% 留出（**按身份切，不能按图切**，否则泄漏）。
2. **微调 fast-reid**，10 epochs（≈ 4.7 小时，而非 20 epochs）。
3. **用现成脚本评测**：`scripts/eval_cross_camera.py`（Rank-1/5/mAP）与
   `scripts/eval_chain_idf1.py`（IDF1），与当前基线直接对比。
4. **判据（先写死，避免事后找理由）**：
   - 若留出身份的 Rank-1 **未超过当前 20.1%**，判定域内微调在本数据量下**不成立**，停止投入；
   - 若显著超过，再评估扩到 20 epochs 与属性侧标注的性价比。

这套实验的增量成本只有 **~4.7 小时 GPU + 写一个切分脚本**，且结论可证伪。

---

## 七、本任务不做什么

- **不执行微调**（本文只做成本评估，执行需另行授权）。
- **不因为"指标难看"而放松评测口径**：IDF1 的 0.4955 与 T1 的 28.4% 都是真实数字，
  不接受用"有条件口径"（如 T1 的 52.6%）替代主口径来充数。
- **不假设换权重就能解决**：分辨率这一项是成像阶段就注定的，换模型无效。

---

## 八、一句话结论

**ReID 域内微调是唯一"标签现成、成本可控（估 ~9.4h GPU）"的路径，但受 218 个身份的小样本
与 116×94 px 的低分辨率双重压制，预期收益有限且需先做 4.7 小时的最小实验证伪；
属性侧微调则被"无域内属性真值"直接阻塞，前置成本是人工标注。**
